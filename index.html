이 회의는 AiVATAR Studio와 V-GEN 라이브 서비스의 화면·플로우를 순서대로 시연하고, 통합 대시보드에서 무엇을 어떻게 합칠지 구두로 설명하는 자리였습니다. 후반부에는 제품 지향점 문서 공유와, 데이터드리븐디자인의 스토리북 기반 작업 방식 시연이 이어졌습니다.

기존 프로젝트 문서(00~06, 화면정의서 7부, 제안서 v0.2)와 대조한 결과 회의에서 설명된 통합 요구사항은 대부분 이미 화면정의서에 문서화되어 있습니다. 따라서 이 회의는 신규 요구 회의가 아니라 문서의 구두 워크스루이며, 실제 논의할 지점은 새로 나온 것이 아니라 문서와 어긋난 것과 문서에 있는데 회의에서 다뤄지지 않은 것에 있습니다.

본 문서는 1부 기록, 2부 논의사항(문서 대조), 3부 다음 회의 준비, 4부 디자이너 의견으로 구성합니다.

Part 1 — 01

AiVATAR Studio — 기존 서비스

단일 화면에서 음성 탭과 영상 탭을 전환하며 작업합니다. 텍스트 에디터는 두 탭에서 유지되고, 영상 탭에서만 사용할 아바타를 고를 수 있다는 점이 차이입니다.

  • 에디터에 대본을 입력하고 문단별로 목소리·언어를 설정합니다.
  • 음성으로 내보내면 해당 목소리의 음성 파일이, 영상으로 내보내면 선택한 아바타가 그 대본을 말하는 영상이 생성됩니다.
  • 핵심 기술은 음성의 발음에 맞춰 입 모양을 생성하는 것. 말하지 않는 촬영 영상을 발화 영상으로 바꿉니다.
  • 셀프 커스텀 아바타 — 30초~1분 촬영본을 업로드하면 리와인드되며 발화합니다. 목소리도 만들 수 있어 TTS 음성과 합쳐집니다.

한계와 고객 대응

산출물은 최종 영상이 아니라 크로마키된 영상 소스다. 외부 편집 툴을 다룰 수 있어야 그대로 쓸 수 있고, 그렇지 않으면 배경 제거·편집이 필요합니다. 셀프 커스텀 아바타는 배경을 정해 촬영하므로 편집 없이 쓰는 경우도 있으나, 기본 사용 방식은 발화 영상 소스를 가져가는 것입니다.

편집 인력이 없는 고객은 영상 외주 제작사에 의뢰하거나 AI PARK 내부 제작팀에 별도 상품으로 의뢰합니다. 140개 언어를 지원해 다국어 콘텐츠를 다량 제작해야 할 때 의뢰가 들어오는 경우도 상당수.

Part 1 — 02

V-GEN — 올해 론칭

목표는 하나였습니다 — 영상 편집 툴을 다룰 줄 모르는 사람도 최종 영상본을 가져갈 수 있게 합니다. 대시보드는 처음부터 통합을 염두에 두고 최소 기능(프로젝트 목록·내보내기 목록)만 넣었습니다.

  • 시작 방식 선택 — 대본 직접 입력 / 문서(한글·텍스트) 업로드 / PPT·PDF 장표 업로드(장표를 이미지화해 장면으로 전환) / 빈 화면.
  • 카테고리 선택 — 뉴스·홍보·교육·안내. 다음 단계에서 해당 스타일 템플릿을 먼저 보여주는 편의 기능이자, LLM 톤에 영향을 준다(뉴스=사실 전달, 홍보=관심도 중심).
  • 템플릿 선택 — 디자인이 완성된 템플릿에 정해진 요소만 텍스트로 입력하는 방식. 장면 구성을 미리 확인할 수 있고 가로형·세로형이 있습니다.
  • 아바타 선택 — Studio 대비 개선. 그룹별 구분, 의상·의상 색상·제스처 단계 분리, 필터, 목소리 선택.
  • 스토리보드 생성 — 첫 화면 입력을 기반으로 LLM이 장면별 대본·자막 초안을 채워 넣습니다. 현재 기본 10장면.
  • 자료 화면 구성 — 생성(외부 API·크레딧 차감) / 스톡 검색 / 보관함 / 직접 업로드. 장면에 맞는 프롬프트를 LLM이 미리 제안합니다. 로고·배경음악도 이 단계에서 얹습니다.
  • 미리보기 → 영상 생성 — 미리보기는 이미지 형태만 제공(엔진 비용 때문에 크레딧 미차감). 생성 시 차감 크레딧을 고지하고 확인 후 영상 목록으로 이동, 완료되면 자동 전환.

장면 단위 구조

타임라인이 익숙하지 않은 사용자를 위해 "장면"이라는 단위로 구분했습니다. 한 장면에 기본적으로 하나의 나레이션이 들어가고, 장면을 더 길게 가져가고 싶으면 컷을 추가합니다. 컷을 추가하면 화면 전환 없이 아바타가 계속 발화하고 뒤의 자료 화면·자막만 바뀝니다.

Part 1 — 05

제품 지향점

한 줄 요약 — 누구나 쉽게 들어와 본질적 문제를 풀고, 기대 이상의 결과물로 효능감을 느끼고, 자랑하고, 함께 커지는 서비스.

  • 01 · 심플가벼운 입력, 기대 이상의 결과. 지금도 어렵다는 반응이 있어 진입 장벽이 느껴지지 않았으면 합니다.
  • 02 · 본질화려함보다 본질. "여기서 네 문제를 해결할 수 있어"라는 뉘앙스. 인터페이스 기능을 자랑하기보다 결과물이 돋보이게. 차갑고 미래지향적인 톤보다 사람 친화적인 느낌.
  • 03 · 효능감자랑하고 싶은 결과물. 투두 리스트처럼 혼자 처리하고 끝나는 게 아니라 "편집 없이 나 혼자 이렇게 만들었어"가 되게.
  • 04 · PARK함께 키우는 생태계(먼 미래). 다른 유저가 어떻게 쓰는지 보이면 "이렇게까지 퀄리티 높게 쓸 수 있구나"가 어필됩니다. 사명의 '파크'가 담은 지향.
  • 인지설명이 필요한 부분은 "이걸 누르면 설명을 볼 수 있겠구나"가 인지되면 좋겠다는 것입니다. 화면을 봤을 때 "여기서 이렇게 하면 되겠구나"가 직관적으로 왔으면.

현재 사용자 문제

잘 쓰는 사람은 이 기능 저 기능을 조합해 좋은 결과를 내지만, 영상에 대한 기본 개념이 없으면 기본값만 채워 단조로운 영상을 만드는 경우가 더 많다. 자유도를 원하는 파트(아바타 위치·크기 조절)와 "이것조차 어렵다"는 파트가 양쪽으로 나뉘어 있습니다.

위치·크기 조절은 내부적으로는 가능하지만, UI에서 어떻게 해야 조절이 쉬울지 · 한 컷만 적용할지 전체 적용할지가 고민되어 아예 빼고 괜찮아 보이는 값으로 고정한 개념이 템플릿입니다.

다음 단계로 대화형 에이전트화를 준비 중입니다. 기본 지식이 없어도 요구만 하면 알아서 편집해주는 방향이며, 이번 작업은 그 전 단계로 봅니다.

Part 1 — 07

작업 방식 — 스토리북 SSOT

데이터드리븐디자인이 자체 예제 서비스로 시연한 문서 계층과 운영 방식.

  • Project Summary — 어떤 서비스인지 명세
  • UX Flow — 시나리오별 정리. 이 두 문서를 플래닝 스킬에 통과시키면 필요 컴포넌트 리스트가 도출됩니다
  • Visual Direction — 프로젝트에 맞게 디자인 토큰을 커스텀. UX와 맞닿은 시각 특징을 입력값으로 삼습니다
  • Data Bridge — 시나리오에 등장하는 데이터 모델을 기획자·디자이너가 함께 공유·결정. UX 문서가 SSOT가 되려면 데이터 모델도 기획·디자인의 손을 거쳐야 합니다
  • AI Task — LLM 프로세스를 단계별로 정리. 각 프로세스가 어떤 의사결정과 인풋으로 처리되는지 문서화

운영 방식

  • 페이지 단위까지 스토리북에서 컴포넌트로 관리 → 디자인 측은 프로덕션 코드에 관여하지 않고 스토리북 안에서 해결합니다.
  • 개발은 "레고 블록"을 가져다 로직·API만 연결합니다. 템플릿 이상 컴포넌트의 props가 실제 데이터 모델을 고려해 만들어지기 때문. 문제가 생기면 스토리북으로 돌아와 같이 점검합니다.
  • 기획·기능·데이터 모델이 바뀌면 문서를 먼저 고치고, 그 문서 기준으로 템플릿을 리팩터링합니다. 모든 사람이 같은 문서를 보고 작업합니다.
  • 같은 레포에 있어도 문제없습니다. npm 배포까지는 불필요하고, 사내 Vercel 배포로 내부 인원이 열람하면 됩니다.
  • CLAUDE.md에는 꼭 필요한 컨벤션만 넣는다(매번 읽히므로). Component Work 스킬은 작업 전에 디자인 시스템 인덱스를 먼저 읽고 조립할지 새로 만들지 판단합니다.
  • design.md는 쓰지 않습니다 — MD는 SSOT 역할을 못 하기 때문. Visual Direction이 그 역할을 하되 토큰 커스텀 시 한두 번만 쓰고, 그 외에는 고정 가능한 데이터를 컨텍스트로 씁니다.
  • 스토리북은 Figma와 달리 Claude 연동이 불필요하다. 이미 빌드되어 웹에서 즉시 갱신을 확인할 수 있다(마우스로 못 바꿀 뿐).

회의 후 정리한 관점

회의에서 오간 내용을 바탕으로 데이터드리븐디자인이 정리한 의견입니다. 페르소나 · 통합 방향 · 사각지대 세 가지입니다.

01 · 현시점의 페르소나 차이

AI 아바타의 페르소나와 V-GEN의 페르소나가 어느 정도 겹치는지에 대한 논의가 필요해 보입니다.

설명을 들었을 때 AI 아바타 사용자는 영상 편집이 가능한 사람이었습니다. 그렇다면 이분들이 인하우스 영상 편집자인지, 외주 영상 편집자인지에 따라 유저 저니맵에 차이가 있을 것으로 보입니다.

사용자 유형V-GEN 전환 가능성함의
인하우스 영상 편집자비교적 높음같은 조직 안에서 완성 영상까지 필요해지는 흐름이 이어질 수 있음
외주 영상 편집자낮음소스만 받아 자신의 작업 환경에서 마무리하는 구조

두 유형의 비중이 확인되면 통합 대시보드에서 두 서비스를 어떻게 이어 붙일지의 근거가 됩니다.

02 · 통합 과정의 방향

받은 인상은 두 서비스의 통합이라기보다 V-GEN이 AI 아바타를 흡수하는 것에 가깝습니다.

통합 서비스(가칭)의 핵심 가치 — 한 문장

조직의 얼굴과 목소리를 담는 AI 영상 제작 시스템

기존 두 서비스가 제공하는 두 가지 산출물의 기능 중심 사고에서 벗어나, 이 서비스 밖에서 사용자들이 지향하는(혹은 해야 하는) 바가 무엇인지 — 가장 명확한 꼭지를 시작점으로 인식해야 합니다.

결국 돕는 것은 "조직의 핏에 어울리는 아바타(얼굴과 목소리)로 필요한 영상을 제작하는 과정"입니다.

잡아야 할 멘탈 모델내용
조직의 자산아바타 · 목소리 등 조직을 대표하는 것
콘텐츠 자산영상에 들어갈 재료
최소한의 결정그 자산으로 영상을 만듭니다

이렇게 잡는 이유는, 서비스의 가치와 맞닿아 있는 요소를 먼저 각인시키고, 나머지 정보의 분류 기준 또한 여기에 얼라인해야 서비스 사용이 일맥상통하기 때문입니다.

예시

아바타 선택 기준

지금 아바타를 고르는 기준은 패션 룩북처럼 외형을 사용자가 직접 보고 고르는 형태입니다.

이 분류 기준을 애초에 조직·콘텐츠의 성격에 맞게 조절하는 UX로 보여주면 — 설사 당장 아바타가 그 기준에 100% 부합하지 않더라도 — 사용자가 큰 의사결정 단계를 빨리 인식하고 그 안에서 필요한 세부 조정을 하게 되어 인지 비용이 줄어듭니다.

전제 조건

지금 시점에서는 신규 기능 추가가 아니라, 기존 최말단 기능들을 어떻게 재분류·그루핑할 것인가의 문제로 가져가는 것이 적합해 보입니다. 원천 기술의 개발 소요 없이 다룰 수 있는 범위입니다.

03 · 사각지대

회의에서도 말씀드렸듯, 기존 유저들의 행동 패턴과 실제 사용 시나리오가 아직 잘 드러나 있지 않은 것 같습니다.

기존 유저 피드백과 유저들이 만든 영상들을 쭉 나열해보면, 거기서 발견되는 패턴이나 루틴을 유추해볼 수 있겠습니다.

예시

제주도청 사례에서 유추할 수 있는 것

제주도청의 영상이 콘텐츠 시리즈에 맞게 유사한 아바타나 세팅을 반복해서 사용했다면, 다음과 같은 방식이 가능합니다.

  • 영상을 생성할 때마다 아바타를 세팅하는 것이 아니라, 역할별로 아바타를 등록하고 그것을 조직 자산으로 인식하게 합니다
  • 콘텐츠 유형에 따라 미리 등록된 세팅을 재활용하는 방식으로 만듭니다

쟁점 · 음성 재생과 영상 재생을 나눌 것인가
  • 현재 상태확인 수단은 [미리듣기] 하나입니다. 하단 재생 바(이전·다음 문장 · 타임라인 · 경과 · 전체 예상 시간)는 발화 시간축 위에서 돌고, 3열의 세로 무대는 정지 프리뷰입니다(아바타·의상·배경을 확인하는 자리). 발화 영상 원본이 편당 최대 218MB라 무대에 영상을 걸지 않았습니다.
  • 왜 질문이 되나내보내기는 영상과 음성 2종이고 조건도 다릅니다(영상 = 대본 + 아바타 / 음성 = 대본만). 산출물은 둘인데 만들기 전에 확인하는 수단은 하나입니다. 영상으로 내보내는 사용자는 결과를 내보낸 뒤에야 봅니다.
  • 나눌 경우[음성 듣기]와 [영상 보기]가 각각 진입점을 갖습니다. 영상은 아바타 발화 영상과 합성이라 즉시 재생이 아니라 대기가 붙고, 미리보기 자체에 비용을 물릴지 · 저해상이나 워터마크로 낮출지 정책이 필요합니다. 상단·하단 액션이 늘어 밀도도 올라갑니다.
  • 안 나눌 경우지금 구조 유지. 재생은 음성 확인 전용, 영상은 정지 프리뷰로 구성만 확인. AS-IS와 같은 구조라 기능 제약도 없고 학습 비용도 0입니다. 대신 「영상이 어떻게 나오는가」는 내보내기 전까지 알 수 없습니다.
  • 결정에 필요한 것① AS-IS 또는 백엔드가 영상 미리보기를 제공할 수 있는지(형태 · 대기 시간) ② 미리보기에 크레딧을 차감하는지 ③ 확인 단위가 문장인지 전체인지(재생 바는 이미 문장 단위 이동을 갖고 있습니다).
  • 제안기능 제약이 확인되기 전까지는 현행 유지를 권합니다. 다만 지금은 버튼 이름이 「미리듣기」라 영상 사용자에게는 무엇을 확인하는 것인지 모호합니다. 나누지 않기로 하면 「음성으로 미리듣기」처럼 대상을 이름에 박는 것이 최소 조치입니다.
그 밖의 J3 논의
  • 01 · 상단 바J3에는 단계가 없습니다(3열을 오가며 다듬는 화면). 스텝 내비를 걷어내고 사용법 · 내보내는 조건 · 지금 할 일 3행 안내로 바꿨습니다. 문서의 「단계 수 미정」을 「J3는 스텝 0」으로 확정받고자 합니다.
  • 02 · 열 구성목소리를 3열에서 2열로 옮겼습니다. 목소리는 문단 단위로 걸리는 값이라 프로젝트 전역인 아바타와 같은 열에 있을 이유가 없습니다(2열 = 음성 세팅 · 문단 기준 / 3열 = 영상 세팅 · 프로젝트 전역). 개발 확인이 필요한 전제입니다.
  • 03 · 아바타 조절프리뷰가 열을 채우고 설정이 그 위에 겹쳐 열립니다. 조절은 아바타 → 의상 색 → 제스처 순번 아코디언(상위를 바꾸면 하위가 풀리는 종속, 회신 355)으로 폈습니다.
  • 04 · 촬영 세트 이름세트 칩에 AS-IS 원본 이름(Jena_V2_01 형태)이 그대로 노출됩니다. 한글 표시명이 데이터에 없어 지어내지 않았습니다. 표시명 규칙 또는 데이터 보강이 필요합니다.
  • 05 · 등급 뱃지아바타 카드의 3번째 뱃지 축(등급)은 회신 144에서 「함께 정하자」로 남았습니다. 위저드 목록과 애셋 페이지의 표현이 일치하느냐가 여기서 갈립니다. 임의 추가하지 않고 대기 중입니다.
  • 06 · 목소리 탐색언어 → (국가) → 목소리 모달로 폈습니다. 국가 단계는 필요한 12개 언어에서만 뜹니다. 검색은 TO-BE에도 없어 넣지 않았는데, 475종 규모에서 페이지네이션만으로 충분한지 확인이 필요합니다.
  • 07 · 서비스 범위AS-IS는 범위가 의상 단위인데 우리는 아바타 단위라, Studio 전용 아바타가 V-GEN 목록에 남습니다. 모델을 의상 단위로 맞출지 결정이 필요합니다.
  • 08 · 뱃지 원칙 긴장내부 규칙은 「모든 항목에 똑같이 붙는 뱃지는 정보가 아니라 장식」인데, TO-BE 처방은 「아바타 카드에 뱃지 2종 부착」입니다. 어느 쪽을 정본으로 둘지 정리가 필요합니다.
결정 대기 · 회신이 있어야 확정되는 것
  • 콘솔 본문 폭 · 회신 사이에 1200과 780/900/1000이 충돌합니다. 폭은 전 화면 레이아웃의 기준선이라 먼저 확정이 필요합니다.
  • 산정식 10건 · 크레딧 차감식 · 재생 시간 산정식 · 장면 요소 값의 범위 등. 문서에 없는 값을 지어내지 않고 코드에 「회신 대기」로 표시해 두었습니다. 현재 수치는 기존 상수를 역산해 맞춘 것입니다.
  • 정본 확정 2건 · 컴포넌트 계층 트리가 최근 재작성을 아직 반영하지 못한 것 · 스토리보드 「준비 완료」 판정 근거 미정의.
  • 템플릿 2필드 · 필요 소재와 자료화면 개수는 AS-IS 응답에 없습니다. 우리가 파생하거나 비워 둔 상태입니다.
